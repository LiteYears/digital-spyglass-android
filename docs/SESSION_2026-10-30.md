## Watch (monitor) — semantic correctness + release preparation

1. **Unreachable-attribution fix, live-verified.** A fake `.onion`
   produced the same Java `SocketException("SOCKS…")` class as a dead
   Tor daemon, so the original notification claimed "Tor unavailable"
   while Tor was demonstrably working. Resolution: run-level
   attribution with a two-probe design — a SOCKS5 greeting (proves the
   local proxy answers) plus, only in the ambiguous all-dead-online
   case, a circuit probe (SOCKS connect through Tor to
   `www.torproject.org:80`, proving circuit+exit capability; bounded
   to at most one extra circuit per run). Observed on device via
   `dumpsys notification`: `"All checks inconclusive — services
unreachable or descriptors missing; Tor itself is reachable"` and,
   in a partial-failure run, `"1 check inconclusive — service
unreachable or descriptor missing"`. Evidence: device dumpsys.

2. **R1 persistence exception narrowed.** `lastSummary` (aggregate
   category counts of the last run) was moved to memory-only.
   Persisted state is now two timestamps (`lastAttemptAt`,
   `lastSuccessfulCheck`) plus one findings bit (`badgePending`).
   Post-restart the UI reports findings without reconstructing
   details. Evidence: source inspection, doctrine text.

3. **Notification-permission gate.** `POST_NOTIFICATIONS` denial on
   Android 13+ silently suppresses all output. On-device observation:
   `importance=NONE, numEnqueuedByApp=6, numPostedByApp=0`. The app now
   exposes a persistent in-app banner ("Notifications disabled —
   Watch cannot report results"), a badge fallback at every
   notification level, and a `Log.w` audit line. Evidence: device
   dumpsys (denial observed), unit test for the helper, source
   inspection (banner/fallback paths). The denied-permission UI was
   verified after granting via adb; a fresh-install denied-state
   hardware pass is still pending — see Open items.

4. **Typed failure taxonomy extended.** `NOT_WATCH_ENVELOPE` was added
   (previously folded into `CORRUPT_ENVELOPE`). The taxonomy is now 10
   distinct `RunResult` states, each with a distinct UI message. The
   `WRONG_PASSPHRASE` path was accidentally exercised live when a test
   envelope was generated with a mismatched passphrase — it surfaced
   its own message, not a generic failure. Evidence: device
   observation (incidental), unit tests.

5. **Permission-rule correction.** A per-item `isOnline()` early
   return gated network operations on connectivity state — a real
   violation of the rule that `ACCESS_NETWORK_STATE` may label but
   never gate. Removed; connectivity now only classifies at run level.
   Evidence: source inspection (before/after).

6. **Release preparation.** Custom launcher icon (adaptive vector +

## Resolved in-session: implicit-DNS leak in TorChecker (found by review, fixed, device-verified)

Late-session review of the Pi-hole decisions-log entry caught a real
defect that a `getByName` grep structurally cannot find:
`new InetSocketAddress(String host, int port)` _attempts_ resolution
internally (per JavaDoc — the implicit `getByName` lives inside the
constructor). Consequences measured in `TorChecker`:
`.onion` item connects emitted a doomed local DNS query per attempt;
the `www.torproject.org` circuit probe resolved **successfully** on
every run — a live DNS leak of a Tor-related lookup. Fix: all
remote-target addresses switched to `InetSocketAddress.createUnresolved`
(two sites; proxy-side `127.0.0.1` literals unchanged — numeric
literals never emit DNS). Device-verified on SM-G998B via the `check`
diagnostic path: fake onion → `UNREACHABLE_CIRCUIT` (probe path
exercised), Ahmia onion → `UP`/200 (remote resolution intact).
Residual honesty narrowed same day: Tor's own `TestSocks 1` oracle
(set in Orbot's custom-torrc) logged `NOTICE: …instructed Tor to
take care of the DNS resolution itself if necessary. This is good.`
for both the Ahmia `.onion` connect and the fake-onion/probe path —
zero `warn` lines. Precise scope: **Tor-observed DNS silence is
verified** — every connection Tor received was hostname-based. A
non-SOCKS stray query would be invisible to this oracle; the
five-site inventory makes it unlikely but unproven, so the AdGuard
full-packet test remains the one residual. `TestSocks 1` stays
enabled as a standing canary: a future resolution regression logs a
`warn` without anyone re-running the check.
Follow-up audit of the remaining paths (same review): HTTP is manual
over the raw socket — no client library exists, so the OkHttp
`Dns.SYSTEM` leak class is structurally absent; redirects cannot be
followed because the parser never reads `Location:` and any non-200
returns `DOWN_HTTP`. The whole network surface is five
`InetSocketAddress` sites in one file. Follow-on review audited the
hand-rolled parser's own bounds (the price of rejecting a client
library): `MAX_BODY_BYTES = 256 KiB` caps every body read; matcher is
a byte-level case-folded substring scan — no regex, no ReDoS;
malformed status lines fail closed to `DOWN_HTTP(0)`. Review then
found the concept's "per-item deadline 45 s" was **specified but not
implemented** — at `PARALLELISM=8`, eight hostile peers streaming
headers at <30 s cadence could have held every slot until the
90-minute `awaitTermination` cap. Fixed properly rather than
re-categorized: `ITEM_DEADLINE_MS` now bounds each item across its
one retry — and the connect call itself takes the remaining budget
as its timeout, so the 45 s is exact, not an approximation.
Device-verified again post-fix: Ahmia `UP`/200, fake onion
`UNREACHABLE_CIRCUIT`. The response-content layer was then
inventorized the same way: the request advertises HTTP/1.0 with no
`Accept-Encoding`/`Accept-Charset`, so compliant servers cannot send
chunked or compressed bodies — both classes eliminated at the
protocol level, not by parser code. Meta-refresh/JS redirects are a
named semantic blindness (parser reports `UP` on a redirect page;
following would cost HTML execution). The under-read false-negative
(signature past a lying `content-length` is missed) remains open,
named on the correct axis in `DECISIONS_LOG.md` entry two. The verification rule was
sharpened in `GHOST_WATCH_CONCEPT.md` and the corrected history
recorded in `DECISIONS_LOG.md` — including the fact that this entry's
first version carried the false positive it now corrects.
